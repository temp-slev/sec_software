## Реализация

FastAPI хранит товары в PostgreSQL. Redis кэширует `GET /items/` на 30 секунд;
успешный `POST /items/` сбрасывает кэш. Nginx принимает HTTP-запросы на порту 80 и
распределяет их между репликами приложения. Приложение пишет логи в stdout и в
файлы общего Docker volume; каждая реплика имеет отдельный файл с ротацией.

| Файл | Назначение |
|---|---|
| `app/main.py` | API, PostgreSQL, Redis и логирование |
| `app/requirements.txt` | зависимости приложения |
| `Dockerfile` | образ Python 3.12, запуск под UID 10001 |
| `docker-compose.yml` | PostgreSQL, Redis, FastAPI, Nginx; pgAdmin в профиле `admin` |
| `nginx/default.conf` | reverse proxy с обновлением адресов реплик через Docker DNS |
| `verify.py` | воспроизводимая проверка API через Nginx |
| `logs/` | результаты выполненных проверок |

Эндпоинты: `GET /`, `GET /health`, `POST /items/`, `GET /items/`, `/docs`.
`X-Cache: MISS/HIT/BYPASS` показывает источник ответа; `X-Instance-ID` — реплику,
обработавшую запрос. Параметры SQL передаются отдельно от текста запросов.

## Выполнение этапов и самостоятельных заданий

1. Docker и Compose проверены в окружении macOS / Docker Desktop (Linux-контейнеры arm64).
2. Создано приложение с таблицей `items`, уникальным именем товара, обработкой дубликатов
   (HTTP 400), валидацией цены (HTTP 422), созданием таблицы при старте.
3. Собран образ и выполнен отдельный запуск контейнера приложения с доступом к БД и Redis.
4. Сервисы развёрнуты через Compose. `depends_on` ожидает успешных healthcheck БД и Redis;
   Nginx ожидает готовности приложения. pgAdmin предусмотрен как необязательный сервис.
5. Проверены API, логи, выполнение команды внутри контейнера и масштабирование приложения
   до двух реплик через Nginx.
6. Сравнение VM, Docker и LXC приведено ниже. Необязательное развёртывание LXC не выполнялось:
   текущая платформа — macOS с Linux-ВМ Docker Desktop.

**Задание 1:** Redis, кэширование GET, инвалидация при записи. PostgreSQL остаётся
источником данных; при ошибке Redis чтение переключается на БД. WATCH и счётчик версии
предотвращают запись устаревшего кэша конкурентным GET после инвалидации.

**Задание 2:** отдельный Nginx принимает запросы на `http://localhost:80`.

**Задание 3:** именованный том `app_logs` сохраняет файлы логов при пересоздании
контейнеров; том `postgres_data` сохраняет товары. Проверено сохранение после удаления
и повторного создания контейнеров без удаления томов. В Docker Desktop тома находятся
внутри Linux-ВМ на диске Mac, а не в каталоге проекта.

## Отличия от листинга методички

- Приложение не публикует фиксированный порт и не имеет `container_name`: иначе
  `--scale app=2` вызвал бы конфликт имён и портов. Внешний порт принадлежит Nginx.
- Удалено bind-монтирование `./app:/app`: в исходном листинге оно скрывало путь
  `app.main`, заданный Dockerfile. Исходники копируются в образ.
- Синхронный драйвер PostgreSQL вызывается в обычных `def`-эндпоинтах — FastAPI
  выполняет их в пуле потоков. Соединения закрываются и при ошибках.
- Отдельный запуск контейнера тоже использует сеть с PostgreSQL и Redis: без БД
  исходный пример не смог бы пройти создание таблиц при старте.
- Используются Compose V2 и актуальный механизм lifespan вместо `on_event`.
- Ключи в `.env.example` — демонстрационные значения для локального стенда.

## Сравнение способов изоляции

| Свойство | VM | Docker | LXC |
|---|---|---|---|
| Что изолируется | целая ОС со своим ядром | приложение и его зависимости | пользовательская среда Linux, часто с init и несколькими службами |
| Ядро | отдельное гостевое | общее с Linux-хостом | общее с Linux-хостом |
| Запуск и ресурсы | обычно больше времени и памяти | быстрый запуск процессов | обычно легче VM; зависит от состава системы |
| Типичный сценарий | другая ОС, отдельное ядро | упаковка и масштабирование сервисов | системные Linux-контейнеры |
| Ограничение | накладные расходы | ошибки ядра затрагивают границу изоляции | также зависит от безопасности общего ядра |

На Mac Docker Desktop запускает Linux-ВМ, внутри которой работают Docker-контейнеры.
Поэтому Docker здесь тоже использует виртуализацию, а Linux-контейнер не исполняется
непосредственно на ядре macOS. Привилегированные контейнеры и монтирование сокета Docker
существенно ослабляют изоляцию; в приложении они не используются.

## Ответы на контрольные вопросы

1. **VM / Docker / LXC.** VM имеет собственное ядро и виртуальное оборудование. Docker и LXC
   используют namespaces и cgroups общего Linux-ядра. Docker обычно упаковывает приложение,
   LXC — системную среду; это распространённые сценарии, а не запрет нескольких процессов.
2. **COPY и ADD.** COPY копирует файлы из контекста сборки или другого этапа. ADD дополнительно
   поддерживает удалённые источники и автоматическое распаковывание локальных tar-архивов.
   Для исходников и requirements достаточно COPY.
3. **Ожидание зависимостей.** `depends_on` с `condition: service_healthy` ожидает healthcheck.
   Простая запись `depends_on` определяет порядок запуска, но не готовность сервиса.
4. **Сеть Compose.** Compose создаёт bridge-сеть; DNS разрешает имена сервисов (`db`, `redis`,
   `app`). Межконтейнерный обмен использует внутренние порты. Публикация нужна для доступа с хоста.
5. **Хранение.** Named volumes управляются Docker и сохраняются независимо от контейнеров.
   Bind mounts отображают конкретный путь хоста. tmpfs хранит временные данные в памяти.
   Удаление томов уничтожает сохранённые в них данные.
6. **LXC.** Как и Docker, LXC использует namespaces/cgroups, а не отдельное ядро VM. Уровень
   защиты определяется настройками user namespaces, capabilities, seccomp и LSM.
7. **Масштабирование.** `docker compose up -d --scale app=2`. Нужны балансировщик,
   отсутствие фиксированного имени контейнера и конфликтующих портов. Состояние выносится
   в общую БД/кэш; запись разных реплик в один ротируемый лог-файл следует исключить.
