## Ответы на контрольные вопросы

1. **Минимальные требования.** Официально — 4 ГБ RAM и 2 ядра CPU (для совсем маленьких
   инсталляций, без больших проектов и CI). GitLab включает веб-сервер, PostgreSQL, Redis,
   Sidekiq и Gitaly одновременно на одной машине; при меньшей памяти процесс установки или
   `reconfigure` обрывается по нехватке памяти, либо сервисы начинают падать под Out-Of-Memory
   killer'ом уже после установки.
2. **Postfix.** Используется для отправки email-уведомлений самим GitLab: подтверждение
   регистрации, уведомления о событиях в проектах, сброс пароля и т. д. Без настроенного
   почтового сервера эти письма никуда не уйдут, хотя сам GitLab при этом продолжит работать.
3. **Временный пароль root.** Хранится в `/etc/gitlab/initial_root_password` в открытом
   виде. Файл автоматически удаляется при следующем запуске `gitlab-ctl reconfigure`
   примерно через 24 часа после установки, поэтому пароль нужно сразу сохранить или сменить.
4. **GitLab Runner.** Отдельный агент, который получает задания (jobs) из CI/CD-пайплайнов
   GitLab и выполняет их: клонирует репозиторий, запускает команды из `.gitlab-ci.yml` в
   выбранном окружении (контейнер, shell-сессия и т. д.) и отправляет результат и логи
   обратно на сервер GitLab.
5. **Executor docker и shell.** `shell` выполняет команды джобы прямо в системе, где
   установлен Runner — быстро, но джобы делят окружение и зависимости друг с другом и с
   самой ВМ, слабая изоляция. `docker` запускает каждую джобу в отдельном контейнере на
   основе заданного образа — изоляция от хоста и между джобами, воспроизводимое окружение,
   но требует установленного Docker и выбора образа (как `alpine:latest` в этой работе).
6. **Добавление SSH-ключа.** Сгенерировать пару ключей (`ssh-keygen -t ed25519`), вывести
   публичный ключ (`cat ~/.ssh/id_ed25519.pub`), в веб-интерфейсе GitLab перейти в
   Profile → Preferences → SSH Keys (или User Settings → SSH Keys), вставить публичный ключ
   целиком и сохранить. После этого `git clone`/`push` по `git@<host>:...` работают без
   пароля, аутентификация идёт по приватному ключу на локальной машине.
7. **Проверка Runner'а.** На самой ВМ — `sudo gitlab-runner status`
   (`gitlab-runner: Service is running`) и `sudo gitlab-runner list`. В веб-интерфейсе —
   Settings → CI/CD → Runners: у активного Runner'а зелёный индикатор и отметка «last
   contact» недавним временем.
8. **История пайплайнов.** В интерфейсе проекта: Build → Pipelines (в более старых версиях
   — CI/CD → Pipelines). Там видна история запусков, их статус, а переход в конкретный
   пайплайн открывает список джоб и их логи.
