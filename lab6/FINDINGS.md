# Отчёт о найденных уязвимостях (этап 6)

Цели: собственный локальный кластер Kubernetes (Docker Desktop, `docker-desktop`),
развёрнутые в нём приложения (`fastapi-app` из Лабы 5) и запущенные локально сервисы из
Практики 3 и Лабы 4. Тестирование авторизовано (собственная учебная инфраструктура),
инструменты легальные: nmap, kube-hunter, kube-bench, Kubescape, kubectl, curl.

## Матрица уязвимостей

| Уязвимость | Критичность | Возможное влияние | Рекомендация |
|---|---|---|---|
| IDOR в User Service (Практика 3): `PUT/DELETE /users/{id}` не проверяют владельца ресурса | Высокая | Любой аутентифицированный пользователь может изменить или удалить чужую запись | Связывать ресурс с `user_id` из токена и проверять совпадение перед изменением |
| Отсутствует `securityContext` у `fastapi-app` (Лаба 5) | Средняя | Нет явного запрета повышения привилегий и явного non-root; контейнер защищён только благодаря `USER` в Dockerfile | Добавить `securityContext`: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true` |
| Раскрытие версии Kubernetes через `/version` (kube-hunter, KHV002) | Высокая (по kube-hunter) | Злоумышленник точно знает версию control plane и может подобрать известные CVE для неё | В продакшене `/version` доступен и администраторам полезен; закрыть сетевым периметром / файрволом, не публиковать API-сервер наружу |
| `--audit-log-path` не задан (kube-bench 1.2.16–1.2.19) | Средняя | Нет аудиторского журнала запросов к API-серверу, инцидент сложно расследовать постфактум | Включить audit log control plane (см. ответ на вопрос 6) |
| `--profiling=true` на API Server, Controller Manager, Scheduler (kube-bench 1.2.15, 1.3.2, 1.4.1) | Низкая | `/debug/pprof` раскрывает внутренние данные процесса | Выставить `--profiling=false` |
| 172 CVE в системных пакетах базового образа `python:3.12-slim` (Kubescape scan image) | Высокая (55 High) | Уязвимости ОС-уровня (`util-linux`, `perl-base`, `zlib1g`, `libc6` и др.), не в коде приложения | Регулярно пересобирать образ на свежий `python:3.12-slim` или перейти на `-slim-bookworm`/distroless; сканировать образы в CI |
| `automountServiceAccountToken` не выставлен в `false` для подов без доступа к API (NSA-скан Kubescape) | Низкая | Токен сервисного аккаунта доступен поду, даже если он не вызывает Kubernetes API | Установить `automountServiceAccountToken: false` там, где доступ к API не нужен |
| Нет NetworkPolicy ни в одном namespace (NSA-скан Kubescape, Ingress/Egress blocked: 0%) | Средняя | Любой под в кластере может обращаться к любому другому поду | Добавить `NetworkPolicy` с явным разрешённым трафиком (default-deny + allow по необходимости) |

Критических уязвимостей (Critical), дающих немедленный полный компромисс, не обнаружено.
Устойчивые механизмы защиты, подтверждённые тестами: анонимный доступ к API-серверу
запрещён (403), kubelet недоступен с хоста, JWT-сервис (Лаба 4) отклоняет подделанный
токен с `alg=none` и не принимает чужой алгоритм подписи, CORS не отражает произвольный
`Origin`, Content-Type switching не обходит валидацию Pydantic, контейнер `fastapi-app`
не привилегирован, без `hostPID/hostNetwork/hostIPC`, без `docker.sock`, выполняется под
непривилегированным пользователем (uid 10001).

## Оценка цепочки атак

Классический сценарий из задания: **SSRF → Metadata → IAM-роль → S3 → kubeconfig → кластер**.
В собственной среде прямого аналога этой цепочки нет (кластер локальный, без облачного
metadata-сервиса), но похожая цепочка здесь возможна в теории:

**IDOR в User Service → чужие персональные данные → подбор пароля на основе утечки →
доступ в соседний сервис с тем же паролем (если пользователь его переиспользует) →
при наличии доступа к Kubernetes API — чтение Secrets в том же namespace.**

Отдельно каждое звено не критично: IDOR без прав в кластере не даёт доступа к
инфраструктуре, а права без начальной точки входа недостижимы снаружи. Но вместе они
образуют путь от уязвимости в приложении до потенциальной компрометации данных. Это и
демонстрирует главный тезис занятия: совокупность небольших недостатков может быть
опаснее одной явной уязвимости.

## Методическое замечание (задание 1)

Первая попытка проверить права `default` ServiceAccount через
`kubectl --token=<SA token> auth can-i --list` дала неверный результат «есть все права»:
kubeconfig администратора уже содержит клиентский TLS-сертификат для этого контекста,
и API-сервер при одновременном наличии сертификата и `--token` аутентифицирует запрос
по сертификату, игнорируя токен. Корректный результат получен через имперсонацию
(`kubectl --as=system:serviceaccount:default:default get pods` → `Forbidden`) и
подтверждён разбором `ClusterRoleBinding`: `default` ServiceAccount не имеет отдельной
привязки ролей, а глобально привязан только `system:public-info-viewer`
(группам `system:authenticated`/`system:unauthenticated`), который даёт доступ лишь к
публичным discovery-эндпоинтам (`/version`, `/healthz`, `/openapi` и т. п.), но не к
`pods`, `secrets` и другим ресурсам.
