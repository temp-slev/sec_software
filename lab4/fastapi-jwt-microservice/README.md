Микросервис `fastapi-jwt-microservice/` выдаёт access и refresh токены, обновляет и
отзывает их, разграничивает доступ по ролям.

## Запуск

```bash
cd fastapi-jwt-microservice
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # задайте SECRET_KEY и ADMIN_CODE
uvicorn app.main:app --reload --port 8000
pytest -q                   # 14 тестов
```

Без `SECRET_KEY` приложение не запускается (`RuntimeError`). Файл `.env` не хранится
в репозитории, образец — `.env.example`. Протокол реального запуска — `run-log.txt`,
коллекция для Postman — `postman_collection.json` (токены сохраняются в переменные
автоматически).

## Эндпоинты

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /`, `GET /public-info` | публичный | информация о сервисе |
| `POST /register` | публичный | регистрация (роль `admin` требует заголовок `X-Admin-Code`) |
| `POST /token` | публичный | вход, форма OAuth2 |
| `POST /token/custom` | публичный | вход, JSON |
| `POST /refresh` | refresh токен | новая пара токенов, старый refresh отзывается |
| `POST /logout` | refresh токен | отзыв refresh токена (blacklist) |
| `GET /protected` | access токен | данные пользователя |
| `GET /protected/admin` | роль `admin` | панель администратора |
| `POST /token/revoke-all` | access токен | отзыв всех токенов пользователя |
| `POST /password` | access токен | смена пароля, отзыв всех токенов |

## Этап 6 и задания

| Требование | Реализация |
|---|---|
| CSRF (проверка заголовков) | middleware отклоняет изменяющие запросы с `Origin` вне `ALLOWED_ORIGINS` (403) |

| Логирование попыток аутентификации | логгер `audit` пишет в консоль и `audit.log` (вход, ошибки, отказы по ролям, отзывы) |
| Задание 1. Роли | поле `role` (`user`/`admin`), передаётся при регистрации; `admin` только с `X-Admin-Code`; `/protected/admin` — только для `admin` |
| Задание 2. Время жизни | `ACCESS_TOKEN_EXPIRE_MINUTES` и `REFRESH_TOKEN_EXPIRE_DAYS` из окружения; `POST /token/revoke-all` увеличивает `token_version` пользователя |
| Задание 3. Секреты | `SECRET_KEY` читается из окружения / `.env` (python-dotenv); без него старт невозможен; тест `test_secret_key_change_invalidates_tokens` подтверждает, что после смены ключа все токены недействительны |
| Rate limiting | не более 5 неудачных попыток входа за минуту на пару IP + логин (429) |

## Проверка в Postman

Импортируйте `postman_collection.json` и выполните запросы по порядку. Ожидаемые коды:
`200`, `200`, `201`, `200`, `401`, `200`, `403`, `200`, `200`, `401`, `200`. Для отчёта
сделайте скриншоты: вход (токены), `/protected` без токена (401) и с токеном (200),
`/refresh`, `/logout` и повторный `/refresh` (401 «Token revoked»).

## Ответы на контрольные вопросы

1. **Части JWT.** Header (алгоритм и тип), Payload (claims: `sub`, `exp`, `type`, …) и
   Signature. Header и Payload — JSON в кодировке Base64URL, подпись — HMAC-SHA256 от
   `header.payload` секретным ключом; части соединяются точками. Payload не шифруется.
2. **Access и refresh.** Access живёт недолго (минуты) и передаётся с каждым запросом, его
   кража даёт ограниченное окно. Refresh живёт дольше, используется только для получения
   новой пары, его можно отзывать и хранить надёжнее. Разделение уменьшает ущерб от утечки.
3. **Стратегии отзыва.** Короткий срок жизни access; чёрный список токенов (blacklist,
   используется для refresh); версия токенов пользователя (`token_version`, отзыв всех
   сразу); ротация refresh с обнаружением повторного использования. В решении: blacklist
   для refresh + `token_version`.
4. **Уязвимости JWT.** Подмена алгоритма (`alg: none`, HS/RS-путаница) — всегда указывать
   `algorithms=[...]` при проверке; отсутствие проверки `exp` — библиотека проверяет её
   по умолчанию; слабый или утёкший ключ — длинный случайный `SECRET_KEY`; приём токена
   не того типа — проверка `type`; хранение в `localStorage` — XSS.
5. **Хранение SECRET_KEY.** Не в коде и не в git: переменные окружения, Docker/Kubernetes
   Secrets, менеджер секретов (Vault, AWS Secrets Manager); регулярная ротация, разные
   ключи для сред, минимальный доступ.
6. **HTTP-only cookies.** Cookie с флагами `HttpOnly` (недоступна JavaScript, защита от
   кражи при XSS), `Secure` (только HTTPS) и `SameSite` (защита от CSRF). Хранение в
   `localStorage` делает токен доступным любому скрипту на странице.
7. **CORS.** `CORSMiddleware` с явным списком `allow_origins` (не `*`), только нужные
   методы и заголовки; при использовании cookies — `allow_credentials=True` вместе с
   конкретными origin. В решении список задаётся переменной `ALLOWED_ORIGINS`.
8. **Rate limiting.** `/token` и `/register` — цель перебора паролей и массовой
   регистрации; ограничение числа попыток замедляет атаку и снижает нагрузку. В решении —
   лимит неудачных попыток; в продакшене добавляют лимит на уровне шлюза/Redis и
   блокировку по аккаунту.
